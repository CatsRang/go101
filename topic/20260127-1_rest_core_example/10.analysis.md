# Core REST API Example with Context-First Architecture

## Overview
This document analyzes the requirements and architectural design for creating a simplified REST API example. The goal is to demonstrate a "Core Architecture" using Go, Echo, Viper, and Cobra, adhering to the "Context-First" principle and Zap logging best practices. The project will be a simplification of an existing (theoretical) domain API, removing persistence (MyBatis) in favor of dummy business logic to focus on architectural patterns.

## Key Files

### Entry Point & Configuration
- `cmd/main.go`: Application entry point. Executes the root Cobra command.
- `pkg/server/server.go`: Core server struct. Manages `echo.Echo` instance, middleware configuration, and lifecycle (start/graceful shutdown).
- `pkg/config/app_conf.go`: Configuration singleton using `viper`. Defines structure for Server, Log, and Worker config.
- `pkg/cmd/root.go`: Cobra root command definition. Initializes config and logger, then starts the server.

### Core Architecture (Context & Middleware)
- `pkg/middleware/context.go`: **Critical**. Middleware to propagate the root server context (with signal handling) to every request.
- `pkg/middleware/logging.go`: Request logging middleware using Zap. Correlates requests with trace IDs.
- `pkg/util/log/logger.go`: Zap logger initialization (Production JSON / Dev Console) and global singleton/context helpers.
- `pkg/util/worker/pool.go`: Generic worker pool implementation supporting `context.Context` for cancellation and graceful shutdown.

### Domain Logic (Clean Architecture)
- `pkg/domain/example/handler.go`: HTTP handlers. Uses `echo.Context` but extracts `ctx` for service calls.
- `pkg/domain/example/service.go`: Business logic. First parameter of methods must be `context.Context`.
- `pkg/domain/example/model.go`: Domain structs.

## Implementation

### 1. Context-First Lifecycle
The application will use `signal.NotifyContext` in `main` (or `server.Run`) to create a root context that cancels on `SIGINT`/`SIGTERM`.
- **Propagation**: This root context is passed to `Server.Setup(ctx)`.
- **Middleware**: A custom middleware will merge this root context with the incoming HTTP request context. This ensures that if the server shuts down, all active HTTP handlers are notified via `ctx.Done()`.
- **Worker Pools**: Background workers are initialized with this root context, ensuring they stop processing when the server stops.

### 2. Web Framework (Echo)
- **Middleware Chain**:
    1. `Recover`: Safety net.
    2. `ContextPropagation`: Injects root shutdown signal.
    3. `RequestID`: Tracing.
    4. `ZapLogger`: Structured logging with request metadata.
    5. `CORS`: Security.
- **Graceful Shutdown**: The `Server` struct will implement a `Shutdown(ctx)` method that:
    1. Calls `echo.Shutdown()` to stop accepting new requests.
    2. Signals worker pools to drain.
    3. Waits for background tasks to complete (with timeout).

### 3. Logging (Zap)
- **Configuration**: configurable level (debug/info) and format (json/console).
- **Structure**: Logs will include standard fields (`time`, `level`, `caller`) and request-scoped fields (`req_id`, `method`, `path`, `status`, `latency`).
- **Optimization**: Use `zap.L()` global or inject logger via struct fields. Avoid `SugaredLogger` in hot paths if possible.

### 4. CLI & Config (Cobra + Viper)
- **Cobra**: Handles command-line flags (e.g., `--config`).
- **Viper**: Loads configuration from YAML/Env. Settings include `Server.Port`, `Log.Level`, `Worker.Count`.

### 5. Simplification (No Persistence)
- **Removal**: All MyBatis dependencies and SQL files are removed.
- **Dummy Logic**: The `Service` layer will simulate work (e.g., `time.Sleep`) to demonstrate context cancellation and return mock data.

## Issues & TODOs

### Current Limitations
- **No Persistence**: Data is volatile and lost on restart.
- **Dummy Business Logic**: Does not represent real-world complexity, only architectural patterns.

### Future Improvements
- **Add Persistence**: Re-introduce a database layer (PostgreSQL/SQLite) using `database/sql` or an ORM, strictly adhering to passing `context.Context` to all DB operations.
- **Metrics**: Add Prometheus middleware for monitoring request duration and worker pool depth.
- **Validation**: Add `go-playground/validator` for request body validation.
