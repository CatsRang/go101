# Implementation Plan: Core REST API Example

## I. Executive Summary
This plan outlines the implementation of a "Context-First" REST API architecture located in `A01.rest_api/04_core_arch/`. The project serves as a reference implementation for high-scale Go systems, featuring robust signal handling, graceful shutdown, and structured logging. The architecture prioritizes the propagation of `context.Context` from the OS signal handler down to individual workers and HTTP requests, ensuring predictable behavior during termination.

## II. Strategic Objectives
- [ ] **Objective 1**: Implement a "Context-First" lifecycle where the root context dictates the lifetime of the server and all background workers.
- [ ] **Objective 2**: Establish a production-grade logging infrastructure using Zap, enforcing structured logging and request correlation (Trace IDs).
- [ ] **Objective 3**: Demonstrate a Clean Architecture layout (Cmd -> Server -> Domain) using standard libraries (Echo, Cobra, Viper) without persistence dependencies.

## III. Phase-by-Phase Roadmap

### Phase 1: Foundation & Infrastructure
- **Description**: Initialize the module and establish the core utilities for configuration and logging. This sets the stage for the server implementation.
- **Technical Tasks**:
  - `go mod init`: Initialize module at `A01.rest_api/04_core_arch/`.
  - `pkg/config`: Implement `AppConf` singleton with Viper to load settings from YAML/Env.
  - `pkg/util/log`: Implement Zap logger factory (Production JSON / Dev Console) and context helpers (`FromContext`, `WithContext`).
- **Definition of Done**: Module initialized, configuration loads correctly, and the logger can output structured JSON to stdout.

### Phase 2: Core Server & Context Logic
- **Description**: Implement the server entry point and the critical context propagation mechanism. This is the heart of the "Context-First" pattern.
- **Technical Tasks**:
  - `pkg/server`: Create `Server` struct holding `echo.Echo`, `AppConf`, and the root `context.Context`.
  - `pkg/server`: Implement `Server.Run()` with `signal.NotifyContext` to capture `SIGINT`/`SIGTERM`.
  - `pkg/middleware/context.go`: Create middleware to merge the server's root context with the HTTP request context.
- **Definition of Done**: The server starts, and hitting `Ctrl+C` triggers the context cancellation signal visible in the logs.

### Phase 3: Middleware & Integration
- **Description**: Wire up the Echo framework with the full middleware stack and CLI integration.
- **Technical Tasks**:
  - `pkg/middleware/logger.go`: Implement Zap middleware to log request details (Trace ID, Status, Latency).
  - `pkg/middleware`: Configure standard Echo middleware (Recover, CORS, RequestID).
  - `pkg/server`: Wire middleware into the `Echo` instance in `Server.Setup()`.
  - `cmd/main.go` & `pkg/cmd`: Implement Cobra root command to boot the `Server`.
- **Definition of Done**: The application runs via CLI (`go run cmd/main.go`), accepts HTTP requests, and logs them with Trace IDs and correct status codes.

### Phase 4: Domain Logic & Worker Pool
- **Description**: Implement a sample domain (`example`) and a worker pool to demonstrate how business logic respects the propagated context.
- **Technical Tasks**:
  - `pkg/util/worker`: Implement a generic `WorkerPool` that drains on context cancellation.
  - `pkg/domain/example`: Create `Model`, `Service`, and `Handler`.
  - `Service`: Add dummy logic (e.g., `time.Sleep`) that checks `ctx.Done()`.
  - `pkg/server`: Register domain routes and initialize the worker pool.
- **Definition of Done**: A `POST /api/v1/example` request triggers a worker job. Shutting down the server while a job is running allows it to complete (or cancel gracefully depending on logic) without error.

## IV. Technical Decisions & Trade-offs
- **Base Directory**: The project root is `A01.rest_api/04_core_arch/`. This avoids unnecessary nesting (`10_context_pattern`) to keep the "core architecture" reference immediate and accessible.
- **Context Propagation**: We use a custom middleware to merge contexts. **Trade-off**: This adds slight overhead per request but is essential for reliable graceful shutdown of long-running handlers.
- **No Persistence**: To focus purely on architectural patterns (Context, Logging, CLI), we use dummy in-memory logic. This simplifies the example but requires a future phase to add a real DB.
- **Zap vs Slog**: We chose Zap for its proven performance and mature ecosystem, especially for complex sampling and rotation needs in high-scale systems.
